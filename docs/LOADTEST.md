# Нагрузочное тестирование: 10 000 000 заметок, 1000 пользователей, 12 месяцев

Выполнено 2026-10-28, 16:48–17:31, на машине разработчика: aarch64, 20 ядер, 121 ГБ ОЗУ
(57 ГБ свободно), NVMe (3.3 ТБ свободно). Все цифры ниже — фактический вывод
`scripts/loadtest/bench.py`. Исходные данные прогонов лежат в игнорируемом каталоге `.tmp/load/*.json`.

## Изоляция
Отдельный контейнер `notetaker-loadtest` (postgres:16-alpine, свой том `notetaker-loadtest-pg`,
порт 127.0.0.1:55432). Настройки под массовую загрузку: `shared_buffers=8GB`,
`maintenance_work_mem=2GB`, `max_wal_size=32GB`, 4 параллельных воркера. Рабочий стек
пользователя (`docker compose`) и его том не затрагивались. Схема — теми же миграциями Alembic.
Backend для измерений — отдельный uvicorn (4 воркера, планировщик выключен, порт 8013).

## Модель данных и её ограничение
Приложение однопользовательское (по ТЗ, без авторизации), в схеме нет пользователей. Поэтому:
- **пользователь** = тег-владелец `user-0001…user-1000` у каждой заметки; «экран пользователя»
  измеряется фильтром по этому тегу;
- **email** пользователя хранится в журнале доставок напоминаний (`reminder_deliveries.email_to`);
- глобальные экраны («Предстоящие», календарь без фильтра) в этой модели показывают данные всех
  1000 пользователей сразу — это заведомо тяжелее любого реального экрана одного человека.

## Найденные и исправленные проблемы
1. **«Предстоящие» разворачивали в Python всю историю** ради итога прошедших (5.7 с на 100k).
   → Развёртка серий и подсчёт в SQL (миграция 0005, сверка с Python-генератором тестами),
   разделы с лимитами и точными итогами.
2. **Тик планировщика загружал все заметки с напоминаниями** (2.1 с на 100k — при 10M
   превысил бы период тика). → Только вхождения ближайших суток с напоминаниями.
3. **Поиск перебирал всю таблицу**: `OR` с подзапросом (добавлен в итерации 2) отключал
   trigram-индексы. Первая замена на `UNION` ускорила редкие слова (78 → 1.2 мс), но на 10M
   замедлила частые (485k id). Финал: `title ILIKE OR body ILIKE OR id = ANY(:ids)` — все
   условия индексируемые, планировщик выбирает сам.
4. **Точный `count(*)` на каждой странице** (214 мс на 9.7M). → Точный до 10 000, дальше
   «10 000+» с флагом `total_capped` (интерфейс показывает «+», а не скрывает).
5. **Сортировка без подходящего индекса** (228 мс для стр. 1, 871 мс для «тяжёлого» тега). →
   Частичные индексы `(start_at, id)` и `(updated_at, id)` по неудалённым (миграция 0006).
6. **Счётчики тегов на каждой форме** (1.8 с). → `/tags?with_counts=false` для форм и
   фильтров (10 мс); счётчики только на странице «Теги», вычитанием корзины (0.8 с).

## Что остаётся медленным и почему (честно)
- **Глобальный календарь и «Предстоящие» по всем 10M** — 1.0–1.7 с. В однопользовательской
  модели это экран сразу 1000 «пользователей»; основное время — развёртка десятков тысяч серий
  в окне и сериализация 5000 вхождений. Экран одного пользователя — 19 мс (типичный) и 0.59 с
  («тяжёлый», 1.65M заметок в год ≈ 4.5 тыс. в день).
- **Глубокая пагинация** (offset 1M) — 0.9 с. Интерфейс предлагает до 500 страниц
  (offset ≤ 10k, 17 мс). Следующий шаг — keyset-пагинация.
- **«Тяжёлый» пользователь + активные + месяц** — 0.36 с: фильтр по тегу и периоду без
  составного индекса по тегу и дате (в многопользовательской схеме решается `user_id` + индексом).
- **Тик планировщика** — 0.6 с раз в 15 с (около 4% одного ядра) при 3.5M правил напоминаний.
- **Многопользовательский режим** не реализован (ТЗ): для настоящих 1000 пользователей нужен
  `user_id` во всех таблицах и индексы, начинающиеся с него; тогда все экраны работают в
  масштабе одного пользователя.

## Как воспроизвести
См. раздел «Нагрузочное тестирование» в README. Контейнер нагрузочной БД после тестов
остановлен (`docker stop notetaker-loadtest`), том сохранён; удалить:
`docker rm notetaker-loadtest && docker volume rm notetaker-loadtest-pg`.
