# DECISIONS — ключевые решения

Формат: решение → причина → последствия/альтернативы.

## D1. Стек — как предложено в задании
FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL 16 + psycopg 3; React + TypeScript + Vite;
TanStack Query; luxon для работы с часовыми поясами в браузере; WebSocket средствами FastAPI;
pytest; vitest (+ Playwright для e2e, если запускается на aarch64).
**Причина:** предпочтительный стек задания, существенных сложностей нет.
Синхронный SQLAlchemy (а не async): проще, тесты прямолинейнее; планировщик работает в отдельном
потоке-цикле с собственными сессиями.

## D2. Среда без Docker → PostgreSQL из pip-пакета
Docker установлен, но пользователь не в группе `docker`. Вместо SQLite (что исказило бы проверку
`ON CONFLICT`, `FOR UPDATE SKIP LOCKED`, advisory locks, `timestamptz`, pg_trgm) используется
настоящий PostgreSQL 16 из пакета `pixeltable-pgserver` (`scripts/dev-db.sh`, порт 5433).
`docker-compose.yml` остаётся основным способом запуска «на чистом окружении».

## D3. Один пользователь, без авторизации
Задание прямо просит не делать авторизацию. Настройки — одна строка `user_settings` (id=1).

## D4. Хранение времени
- Момент заметки: `start_at timestamptz` (UTC).
- `notes.timezone` — IANA-зона, в которой заметка создана/последний раз отредактирована по времени.
  Повторения разворачиваются в этой зоне (09:00 остаётся 09:00 местного при DST).
- Отображение — всегда в `user_settings.timezone`.
- **Смена TZ пользователя не меняет ни одного сохранённого момента**, поэтому `fire_at`
  напоминаний не меняется (требование 4.8). Альтернатива «разворачивать серии в TZ пользователя»
  отвергнута: смена TZ сдвигала бы реальные моменты будущих вхождений и напоминаний.

## D5. Модель повторений
- Правило хранится в самой заметке: `recurrence_freq ∈ {none, daily, weekly, monthly}`,
  `recurrence_until` — локальная дата (в TZ заметки), **включительно**, обязательна для серии.
- Вхождения не материализуются, а вычисляются для запрошенного окна (серия всегда конечна).
- Monthly на 29–31: прижимается к последнему дню месяца, якорь — исходный день месяца.
- Исключения: `occurrence_overrides(note_id, original_start)` — уникальная пара;
  поля `title/body/start_at/is_active` nullable = «наследовать от серии», `is_cancelled` — удалено
  только это вхождение.
- Правка серии: если меняется `start_at`, `timezone` или `recurrence_freq` — все overrides
  удаляются (их `original_start` больше не соответствуют правилу), UI предупреждает. Если
  меняется только `recurrence_until` — overrides сохраняются, вне диапазона игнорируются.
- Удаление серии = в корзину целиком (вместе с overrides); восстановление возвращает как было.
- Неактивная серия → все её вхождения неактивны; активная серия + override `is_active=false` →
  неактивно только это вхождение.

## D6. Напоминания: доставка ровно один раз
- Правила: `note_reminders(note_id, offset_minutes)`, offset ∈ {10, 60, 1440}.
- Событие напоминания: `(note_id, original_start, offset_minutes, fire_at)` — уникальный ключ
  в `reminder_deliveries`. `fire_at` входит в ключ: если вхождение перенесли, у него новое
  напоминание; уже отправленное не повторяется.
- Планировщик (фоновый цикл в процессе backend, период 15 с):
  1. берёт `pg_try_advisory_xact_lock` — одновременно сканирует только один процесс;
  2. разворачивает вхождения в окне, вычисляет просроченные `fire_at ≤ now`;
  3. `INSERT … ON CONFLICT DO NOTHING` — повторный скан/второй процесс ничего не создаёт;
  4. отправка email из outbox: `SELECT … FOR UPDATE SKIP LOCKED` по `status='pending'`,
     отправка, `status='sent'` в той же транзакции.
- In-app: сразу после создания строки события (не дожидаясь email) оно рассылается по WebSocket
  всем вкладкам с `id` доставки. Системное уведомление браузера показывает только вкладка-лидер —
  та, что удерживает Web Lock `notetaker-leader`, пока открыта (`lib/notify.ts`); при её
  закрытии лидерство переходит к другой вкладке. Без Web Locks — запасной вариант с меткой в
  localStorage; дополнительно `Notification.tag` = id. (Первая версия с меткой в localStorage
  давала дубли в e2e: см. WORKLOG 13:21.) Состояние «прочитано» хранится на сервере и
  синхронизируется во все вкладки. Email отправляет только сервер, поэтому число вкладок не
  влияет на число писем.
- Требование задания «однажды показанное не всплывает снова после обновления страницы»:
  показанные в браузере id запоминаются в localStorage (`lib/notify.ts`), и после перезагрузки
  непрочитанные с сервера, уже показанные здесь, не отображаются. В другом браузере или на
  другом устройстве непрочитанное уведомление покажется один раз.
- Остаточный риск: процесс упал после того, как SMTP-сервер принял письмо, но до COMMIT. Тогда
  строка останется `pending` и письмо уйдёт повторно. Строгое exactly-once с внешним SMTP
  невозможно; смягчение — детерминированный `Message-ID` (по ключу события), по которому
  почтовые клиенты/сервера отбрасывают дубли. Максимум 5 попыток, затем `failed`.

## D7. Политика пропущенных напоминаний (простой сервера)
Хранится водяной знак `scheduler_state.last_scan_at`. При скане рассматриваются напоминания с
`fire_at ≤ now` для вхождений, начавшихся после прошлого скана:
- если **вхождение ещё не началось** — напоминание отправляется сейчас; если опоздание больше
  1 минуты и момент напоминания позже последнего изменения заметки, оно помечается `late` (в теме письма «[с опозданием]», в UI — «с опозданием»);
- если вхождение уже началось — напоминание помечается `missed` и **не отправляется**
  (письмо «через 10 минут встреча» после встречи бесполезно);
- первый запуск без водяного знака — отсчёт от текущего момента (историю не досылаем);
- **повторная активация и восстановление из корзины** (требование задания): напоминания, срок
  которых наступил, пока заметка была неактивна или в корзине, **не досылаются** — ни из
  планировщика, ни из очереди писем. Момент активации/восстановления хранится в
  `notes.reminders_resume_at` (миграция 0007), для отдельного вхождения серии — в
  `occurrence_reminder_resume` (миграция 0008, D20);
- то же правило действует, если заметку создали/перенесли так, что момент напоминания уже прошёл,
  а событие ещё нет (например, заметка через 5 минут с напоминанием «за 10 минут»):
  напоминание приходит сразу.

Статусы `reminder_deliveries`: `pending` → `sent` / `failed` (5 попыток), `no_email` (email не
указан — только уведомление в приложении; позже указанный email писем задним числом не шлёт),
`missed`, `cancelled` (D16). Непрочитанные уведомления за 7 дней (по `fire_at`) отдаются `GET /api/notifications`
вкладкам, открытым позже.

## D8. Теги необязательны, удаление тега
Изначально (по формулировке «один или несколько тегов» в `TASK.md`) у заметки был обязателен
хотя бы один тег, и тег, единственный у какой-либо заметки, нельзя было удалить. В PDF задания
сказано «у заметки может быть несколько тегов» — обязательности нет, а запрет удаления мешал
работе с тегами. С 2026-10-29 (итерация 5) теги необязательны: заметку можно создать без тегов,
удаление тега снимает его со всех заметок (включая корзину) и не отклоняется.

## D9. Список и повторения
Список/поиск работает на уровне заметок (серия = одна строка), чтобы фильтрация и пагинация
выполнялись в SQL по всем записям. Фильтр периода для серии — пересечение `[start, until]`
с периодом. Поиск — по полям серии **и** по изменённым заголовку/тексту отдельных неудалённых
вхождений (подзапрос к `occurrence_overrides`, итерация 2); результатом остаётся серия.

## D10. «Предстоящие»
Сервер вычисляет по TZ пользователя: «сегодня» (локальные сутки), «неделя» (пн–вс текущей
недели, без сегодняшних), «прошедшие активные» — **все** активные вхождения с `start < now`.
Изначальное окно 30 дней (итерация 1) убрано в итерации 2: оно незаметно скрывало подходящие
заметки. Ответ ограничен параметром `overdue_limit` (по умолчанию 50, до 1000), но вместе с ним
отдаётся `overdue_total` (итерация 3: «сегодня» и «неделя» тоже ограничены 200 с точными
`today_total`/`week_total`; итоги считаются без развёртки, см. D18), и UI явно пишет «показано N из M» с кнопкой «показать ещё». Хвост
ограничен сверху длиной серий (≤ 5 лет); 5000 прошедших заметок + двухлетняя ежедневная серия —
0.24 с. Клиент пересчитывает принадлежность к «прошедшим» по таймеру без перезагрузки.

## D11. Синхронизация вкладок
Каждая мутация на сервере рассылает по WS `{"type":"changed","entity":...}`; вкладки
инвалидируют кэш TanStack Query. Рассылка — в памяти процесса (один экземпляр backend).
Для нескольких экземпляров потребовался бы Postgres LISTEN/NOTIFY — вне объёма.

## D12. Использование ИИ
Вся разработка ведётся агентом Claude Code (CLI), модель Claude Opus 5.5 (`claude-opus-5-5`).
Промпты и ход работы — в `docs/WORKLOG.md`.

## D13. Поиск без обязательного pg_trgm
Поиск — `ILIKE '%q%'` по `title` и `body` (подстрока, без учёта регистра). Миграция `0001`
создаёт GIN trigram-индексы, если `pg_trgm` доступен (официальный образ postgres — да;
локальная сборка pixeltable-pgserver — нет). Без индекса результат тот же, отличается только
скорость; для тысяч заметок seq scan укладывается в требования (проверяется perf-тестом).
Полнотекстовый поиск (tsvector) отвергнут: он не находит подстроки внутри слов.

## D14. Обнаружение одновременного редактирования (итерация 2)
Оптимистическая блокировка: `notes.version` (миграция `0004`) увеличивается при любом изменении
заметки, её вхождений, удалении в корзину и восстановлении. `PATCH /api/notes/{id}` и
`PATCH …/occurrences/{start}` принимают `version` — версию, с которой клиент начал
редактирование; если она устарела → 409 с понятным сообщением. Проверка выполняется после
`SELECT … FOR UPDATE`, поэтому из нескольких одновременных запросов с одной версией проходит
ровно один (тест на 6 потоках). Форма предупреждает о новой версии сразу (данные приходят по
WebSocket) и предлагает загрузить актуальную. **Итерация 3:** `version` стал обязательным во всех изменениях заметок и вхождений
(PATCH, удаление в корзину, восстановление, окончательное удаление, удаление/сброс/разделение
вхождения); без него — 422. Перетаскивание в календаре передаёт `note_version` вхождения,
переключатель активности в списке — версию из списка. «Последняя запись побеждает» больше нигде
не действует. При конфликте форма предлагает перенести правки пользователя на актуальную версию
(`frontend/src/lib/draft.ts`): переносятся только изменённые поля, поля, изменённые с обеих
сторон, показываются для проверки. Теги (имя и цвет) версий не имеют — изменение тега
атомарно и не теряет связанные данные; это сознательное ограничение.
Альтернатива «сравнивать `updated_at`» отвергнута: точность метки и смена тегов без UPDATE
строки делают её ненадёжной.

## D15. Автоочистка корзины (итерация 2)
Тик планировщика удаляет заметки с `deleted_at` старше `NOTETAKER_TRASH_RETENTION_DAYS`
(30 по умолчанию); связанные теги-связи, исключения, напоминания и журнал доставок удаляются
каскадно. Вкладкам рассылается `changed`. В корзине показана дата окончательного удаления.
Индекс `ix_notes_deleted_start` (первый столбец `deleted_at`) покрывает запрос (EXPLAIN).

## D16. Актуальность письма в очереди и логирование (итерация 2)
Перед отправкой из outbox напоминание перепроверяется: заметка удалена, неактивна, напоминание
отключено, вхождение удалено или время изменено → статус `cancelled` с причиной в `last_error`,
письмо не отправляется (раньше при недоступной почте такие письма уходили позже). Логи
`notetaker.*` настраиваются в `create_app` (`NOTETAKER_LOG_LEVEL`, INFO): раньше uvicorn
показывал только WARNING+, и INFO-сообщения терялись. Сообщения о сбоях почты содержат
доставку, заметку, частично скрытый адрес, попытку N/5 и следующее действие; окончательный
отказ — ERROR. Стадии тика (scan / deliver / purge) падают независимо.

## D17. Изменение серии «с этого вхождения» (итерация 3)
`POST /api/notes/{id}/occurrences/{start}/split`: старая серия заканчивается накануне
выбранного вхождения (по местной дате серии), с него создаётся новая серия с изменениями.
Прошлые вхождения, их исключения и журнал напоминаний не меняются. Если правило не меняется
(то же время, пояс и частота), будущие исключения и записи журнала доставок переходят к новой
серии — уже отправленное напоминание не придёт повторно. Если правило меняется, будущие
исключения удаляются (как при правке всей серии, D5). Разделение с первого вхождения — это
правка всей серии.

## D18. Развёртка серий и подсчёты в PostgreSQL (итерация 3, нагрузочный тест)
Пилот на 100 000 заметок показал, что развёртка в Python не масштабируется (см. LOADTEST.md).
Миграция `0005` добавляет функции `nt_local_to_utc`, `nt_occurrence`, `nt_count_before` с теми
же правилами, что `services/recurrence.py` (настенное время, прижатие к концу месяца с якорем,
несуществующее время — смещение до перехода, неоднозначное — первый момент; PostgreSQL сам
берёт более поздний, поэтому функция корректирует). Python-генератор остаётся эталоном и
используется для операций с одним вхождением; совпадение проверяется тестами
(`test_sql_recurrence.py`). Окно разворачивается между номерами вхождений на его границах —
работа пропорциональна окну, а не истории; подсчёт — арифметикой без развёртки плюс поправки
исключений. Частичный индекс `ix_notes_series_start` по сериям.

## D19. Ограничения ответа на больших объёмах (итерация 3)
Календарь отдаёт не больше 5000 вхождений на окно (самые ранние) и сообщает реальное число
заголовками `X-Truncated`/`X-Total-Count`; интерфейс показывает предупреждение и предлагает
неделю или день. Разделы «Предстоящих» ограничены (200/200/50…1000) с точными итогами. Поиск —
объединение (UNION) условий по trigram-индексам вместо `OR` с подзапросом, который заставлял
PostgreSQL перебирать всю таблицу.

## D20. Повторная активация отдельного вхождения серии (после внешней проверки, 2026-10-29)
Правило D7 «активировали после срока — прошедшие напоминания не досылаются» теперь действует и
для одного вхождения серии. Момент, когда вхождение снова стало активным, хранится в отдельной
таблице `occurrence_reminder_resume (note_id, original_start, resume_at)` (миграция 0008), а не
колонкой в `occurrence_overrides`: «сбросить к серии» удаляет исключение и тоже возвращает
вхождение (в том числе удалённое), и отметка не должна пропадать вместе с ним. Отметка ставится
только при переходе «неактивно → активно»; планировщик и проверка письма в очереди берут более
позднюю из отметок заметки и вхождения.

Текст письма и уведомления в интерфейсе называет реальный остаток времени до начала («через
5 минут»), считая от момента отправки, а не интервал напоминания: напоминание «за 1 день» у
заметки, созданной за 5 минут до начала, или письмо после простоя иначе называли бы неверный срок.
