# TASK.md — Notetaker

## 1. Цель проекта

Разработать полноценное веб-приложение для управления заметками, привязанными к дате и времени. Приложение должно поддерживать теги, календарь, повторяющиеся заметки, напоминания, поиск и фильтрацию.

Главная цель — реализовать не просто демонстрационный интерфейс, а работающий программный продукт с backend, frontend, реляционной базой данных, тестами и документацией.

## 2. Срок и режим работы

- Срок выполнения: 2 дня.
- Инструмент разработки: Claude Code в терминале.
- Работать поэтапно, самостоятельно анализировать требования, реализовывать функциональность, запускать тесты и исправлять ошибки.
- Не останавливаться после создания плана: после фиксации плана переходить к реализации.
- Приоритет: соответствие требованиям, работоспособность, тестируемость и простота запуска.
- Не утверждать, что функциональность работает, если она не проверена.

## 3. Технологический стек

Предпочтительный стек:

- Backend: Python и FastAPI.
- Frontend: React и TypeScript.
- База данных: PostgreSQL.
- Миграции: Alembic.
- ORM: SQLAlchemy.
- Обновления между открытыми клиентами: WebSocket.
- Контейнеризация и запуск: Docker Compose.
- Backend-тесты: pytest.
- Frontend- и интеграционные тесты: подходящие инструменты для выбранного стека.

Если выбранная технология создаёт существенные сложности, сначала оцени альтернативы и зафиксируй обоснование в `docs/DECISIONS.md`.

## 4. Функциональные требования

### 4.1. Заметки

Каждая заметка должна иметь:
- Заголовок.
- Текст.
- Дату и время.
- Один или несколько тегов.
- Статус: активная или неактивная.
- Дату создания и изменения.

Реализовать:
- Создание, просмотр, редактирование и удаление.
- Переключение активности.
- Корзину для удалённых заметок.
- Восстановление заметок из корзины.

### 4.2. Теги

Реализовать:
- Создание, переименование и удаление тегов.
- Изменение цвета тега.
- Привязку нескольких тегов к одной заметке.

### 4.3. Повторяющиеся заметки

Поддержать повторение:
- Ежедневно.
- Еженедельно.
- Ежемесячно.

Для повторения должна задаваться дата окончания.

Пользователь должен иметь возможность изменить или удалить только одно вхождение повторяющейся заметки, не изменяя всю серию.

Продумать хранение правил повторения и исключений. Добавить тесты для границ периодов, окончания серии и изменения отдельного вхождения.

### 4.4. Напоминания

Для заметки можно настроить одно или несколько напоминаний:
- За 10 минут.
- За 1 час.
- За 1 день.

Для активной заметки при наступлении времени напоминания:
- Отправлять email.
- Показывать уведомление в приложении, если браузер открыт.

Каждое напоминание должно отправляться ровно один раз. Повторный запуск обработчика, перезапуск сервера или несколько открытых вкладок не должны приводить к дублированию доставки.

Email допускается реализовать через локальный эмулятор или тестовый адаптер, если реальный почтовый сервис не настроен.

### 4.5. Календарь

Реализовать представления:
- Месяц.
- Неделя.
- День.

На соответствующих датах отображать заметки. По нажатию на заметку открывать её.

Предусмотреть перенос заметки на другую дату перетаскиванием, если это не нарушает модель повторения.

### 4.6. Список заметок

Реализовать:
- Поиск по заголовку и тексту.
- Фильтрацию по тегам.
- Фильтрацию по активности.
- Фильтрацию по периоду.
- Сортировку по дате заметки и дате изменения.

Поиск и фильтрация должны применяться ко всем подходящим записям в базе, а не только к уже отображённым элементам.

Предусмотреть пагинацию и приемлемую производительность на тысячах заметок.

### 4.7. Экран «Предстоящие»

Отображать отдельно:
- Заметки на сегодня.
- Заметки на текущую неделю.
- Активные заметки, время которых уже прошло.

Перемещение заметки в категорию прошедших должно происходить без обязательной перезагрузки страницы.

### 4.8. Настройки пользователя

Предусмотреть:
- Email для напоминаний.
- Часовой пояс пользователя.

Хранить время событий так, чтобы смена часового пояса меняла отображение времени, но не фактический момент отправки уже запланированного напоминания.

## 5. Надёжность и синхронизация

Обязательно проверить:

1. Данные заметок, тегов и напоминаний сохраняются в PostgreSQL.
2. Данные и расписание восстанавливаются после перезапуска backend.
3. Несколько одновременно открытых вкладок получают актуальные уведомления без дублирования доставки.
4. Время отображается в часовом поясе пользователя.
5. При пропущенном во время простоя напоминании действует явно определённая и документированная политика.
6. Повторная обработка одного события не создаёт повторные уведомления.
7. Удаление, восстановление и изменение повторяющихся заметок работают предсказуемо.

## 6. Архитектура и качество

- Frontend и backend должны быть отдельными компонентами, взаимодействующими по сети через API.
- Использовать реляционную базу данных.
- Добавить миграции схемы.
- Разделять бизнес-логику, API, модели и интерфейс.
- Добавить обработку ошибок и валидацию входных данных.
- Не хранить секреты в репозитории.
- Использовать понятную структуру проекта.
- Не добавлять сложные технологии без необходимости.
- Не реализовывать авторизацию, внешние интеграции и дополнительные функции, если они отвлекают от обязательных требований.

## 7. План реализации

Сначала:
1. Изучи весь файл задания и текущую структуру репозитория.
2. Создай `docs/PLAN.md` с этапами и критериями приёмки.
3. Создай `docs/DECISIONS.md` с обоснованием технологий и ключевых архитектурных решений.
4. Создай `docs/WORKLOG.md` с реальной хронологией работы.
5. Создай `docs/TESTING.md` с планом тестирования.

Затем реализуй проект небольшими проверяемыми этапами:
1. Каркас приложения, база данных и запуск.
2. CRUD заметок, теги, активность и корзина.
3. Поиск, фильтры, сортировка и экран предстоящих заметок.
4. Календарь.
5. Повторяющиеся заметки и исключения для отдельных вхождений.
6. Напоминания, email-адаптер и WebSocket-уведомления.
7. Часовые пояса, обработка пропущенных напоминаний и восстановление после перезапуска.
8. Тестирование, документация и подготовка демонстрации.

При необходимости меняй порядок этапов, но документируй причины.

## 8. Тестирование

Для каждого этапа:
- Запускай подходящие автоматические тесты.
- Исправляй обнаруженные ошибки.
- Проверяй интеграцию frontend, backend и базы данных.
- Не заменяй реальные проверки утверждениями в документации.

Особое внимание:
- Повторным напоминаниям.
- Часовым поясам и переходам между датами.
- Изменению отдельного вхождения повторяющейся заметки.
- Перезапуску сервера.
- Одновременной работе нескольких вкладок.
- Поиску и пагинации.

## 9. Документация и отчётность

В процессе работы поддерживай:

- `README.md` — описание, возможности, требования и инструкции запуска.
- `docs/PLAN.md` — план и критерии приёмки.
- `docs/DECISIONS.md` — ключевые решения и причины выбора.
- `docs/WORKLOG.md` — реальные временные отметки, выполненные задачи, проблемы и результаты.

Сохраняй историю Git осмысленными коммитами после завершённых этапов. Не создавай фиктивные коммиты, временные отметки или результаты тестов.

Зафиксируй используемую модель и инструмент, важные промпты и решения агента. Если доступный механизм позволяет экспортировать сессию Claude Code, сохрани экспорт; иначе подготовь собственный журнал с реальными промптами и результатами.

## 10. Критерии завершения

Проект готов к сдаче, когда:
- Его можно запустить по инструкции на чистом окружении.
- Основные операции с заметками и тегами работают.
- Работают календарь, поиск, фильтры и пагинация.
- Реализованы повторения и редактирование отдельных вхождений.
- Напоминания работают без повторной доставки одного события.
- Часовой пояс корректно влияет на отображение.
- Синхронизация между открытыми вкладками проверена.
- Сохранность данных после перезапуска проверена.
- Основные сценарии покрыты тестами.
- Документация отражает фактическое состояние проекта.
- Известные ограничения и следующие улучшения перечислены честно.

В первую очередь заверши обязательные функции и тесты. Дополнительные улучшения делай только после этого.
